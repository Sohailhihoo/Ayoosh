# TOTP Authenticator App 2FA — Design Spec

**Date:** 2026-06-22
**Scope:** Replace email OTP admin 2FA with TOTP authenticator app (Google Authenticator / Microsoft Authenticator)

---

## Overview

Admin login currently uses an email OTP flow. This spec replaces it entirely with TOTP (RFC 6238) — a time-based code generated by an authenticator app. First-time setup happens inside the login flow. Recovery codes provide a self-service fallback if the admin loses their phone.

---

## Data Model

Three new fields added to the `User` schema (all `select: false`):

```js
totpSecret:    { type: String, select: false }
totpEnabled:   { type: Boolean, default: false }
recoveryCodes: { type: [{ code: String, used: Boolean }], select: false }
```

- `totpSecret` — the TOTP secret; only written to the DB after the admin successfully verifies their first code during setup
- `totpEnabled` — gates whether TOTP is required at login
- `recoveryCodes` — 8 single-use codes, stored as SHA-256 hashes; each entry has a `used` boolean

## Backend

### Packages

- `otplib` — TOTP secret generation and token verification
- `qrcode` — generates QR code as a base64 data URL (returned to frontend; no frontend package needed)

### Removals

- `backend/utils/sendOtpEmail.js` — deleted
- `/api/auth/verify-otp` route — removed
- `OTP_TTL`, `OTP_MAX_ATTEMPTS` constants — removed
- Redis keys `otp:*`, `otp_pending:*`, `otp_attempts:*` — no longer used
- `sendOtpEmail` import from `auth.js` — removed

### Modified: `POST /api/auth/login`

Three outcomes for admin users:

| Condition | Response |
|-----------|----------|
| Admin, `totpEnabled: false` | Generate secret + QR URI + 8 recovery codes. Store secret in Redis under `totp_setup:<pendingToken>` (TTL 10 min). Return `{ totpSetupRequired: true, pendingToken, qrUri, recoveryCodes }` |
| Admin, `totpEnabled: true` | Store userId in Redis under `totp_pending:<pendingToken>` (TTL 5 min). Return `{ totpRequired: true, pendingToken }` |
| Non-admin | Issue session immediately — no change |

Recovery codes are 8 codes, each formatted as `xxxxxxxx-xxxx-xxxx` (18 hex chars with dashes, generated via `crypto.randomBytes`), shown to the admin once in plaintext, stored as SHA-256 hashes. The format is intentionally distinct from TOTP codes (6 digits) so the backend can tell them apart without a separate field.

### New: `POST /api/auth/totp/setup/confirm`

First-time setup confirmation.

1. Resolve `totp_setup:<pendingToken>` from Redis → get `{ userId, secret, hashedCodes }`
2. Verify submitted TOTP code against secret using `otplib`
3. On success: save `totpSecret`, `totpEnabled: true`, `recoveryCodes` to User; delete Redis key
4. Issue session (same `createSession` helper)
5. On failure: return error; Redis key remains (admin can retry within TTL)

### New: `POST /api/auth/totp/verify`

Subsequent login verification. Accepts either a TOTP code or a recovery code.

1. Resolve `totp_pending:<pendingToken>` from Redis → userId
2. Load user with `+totpSecret +recoveryCodes`
3. If exactly 6 digits: verify with `otplib.authenticator.verify({ token, secret })`
4. Otherwise (recovery code format): SHA-256 hash the input, compare against stored hashes; mark matched code `used: true`
5. On success: delete Redis key, issue session
6. On failure: return remaining attempts (max 5, tracked in Redis `totp_attempts:<userId>`)

### New: `POST /api/auth/totp/regenerate` (protected, admin only)

Resets TOTP so admin must re-setup on next login.

1. Clear `totpSecret`, set `totpEnabled: false`, set `recoveryCodes: []`
2. Save user
3. Return `{ success: true }`

## Frontend

### Removals

- `verifyOtp` in `store.js` — replaced
- Email OTP UI step in `login/page.js` — replaced

### Login Page (`/login`)

Three-step flow:

**Step 1 — Credentials** (unchanged)
Email + password form.

**Step 2a — First-time setup** (`totpSetupRequired: true`)
1. QR code rendered as `<img src={qrUri} />` with instructions to scan with Microsoft Authenticator or Google Authenticator
2. Recovery codes displayed in a 2×4 grid with a "Copy all" button
3. Checkbox: "I've saved my recovery codes somewhere safe" — must be checked to enable the confirm button
4. 6-digit input to enter first code from app
5. Calls `POST /api/auth/totp/setup/confirm`
6. On success → redirect to `/admin`

**Step 2b — TOTP verify** (`totpRequired: true`)
1. 6-digit input boxes (same UI as current email OTP — reused as-is)
2. "Use a recovery code instead" link — swaps input to a single `<input type="text" />` for the recovery code
3. Calls `POST /api/auth/totp/verify`
4. On success → redirect

### Store (`store.js`)

Replace `verifyOtp` with:
- `confirmTotpSetup(pendingToken, code)` — calls `/auth/totp/setup/confirm`
- `verifyTotp(pendingToken, code)` — calls `/auth/totp/verify`

Both follow the same session-setting pattern as the current `verifyOtp`.

### Admin Settings (`/admin/settings`) — new page

New "Two-Factor Authentication" section:

- Status badge: "Active" (green) or "Not configured" (grey)
- "Regenerate authenticator" button
- On click: confirmation modal ("This will log you out of your authenticator app. You'll need to re-scan the QR code on your next login.")
- On confirm: calls `POST /api/auth/totp/regenerate`, shows success toast
- Admin remains logged in but must re-setup on next login

## Error Handling

| Scenario | Behaviour |
|----------|-----------|
| TOTP code wrong | Decrement attempt counter; return remaining attempts |
| 5 failed attempts | Invalidate `totp_pending` Redis key; force re-login |
| Setup pendingToken expired (10 min) | Return 401; admin must log in again to get new QR |
| Recovery code already used | Return 401 with "Code already used" message |
| All recovery codes exhausted | Admin must regenerate via settings (they're still logged in from current session) |
| Lost phone + no recovery codes | Manual DB reset: `db.users.updateOne({email}, {$set: {totpEnabled: false, totpSecret: null, recoveryCodes: []}})` |

---

## Security Notes

- TOTP secret never returned to the frontend after setup; QR URI returned only once during setup flow
- Recovery codes shown in plaintext exactly once; only SHA-256 hashes stored in DB
- `totpSecret` and `recoveryCodes` fields have `select: false` — never included in normal queries
- Timing-safe comparison used for recovery codes (crypto.timingSafeEqual on hex digests)
- pendingToken is a 32-byte random hex string, stored in Redis with short TTL
